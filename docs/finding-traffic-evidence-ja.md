# 脆弱性の複数トラフィック証拠

> この文書は、上流（オリジナル）の ARTEX 設計文書を日本語に訳したものです。脆弱性とトラフィック証拠を結びつける機能の設計を、貢献者とメンテナーのために記録します。原文（中国語）は [`finding-traffic-evidence-zh.md`](finding-traffic-evidence-zh.md) に保存してあります。
>
> English: **[Vulnerability multi-traffic evidence (finding-traffic-evidence-en.md)](finding-traffic-evidence-en.md)**.
>
> 한국어: **[취약점 다중 트래픽 증거 (finding-traffic-evidence-ko.md)](finding-traffic-evidence-ko.md)**.

脆弱性の詳細画面にある **関連トラフィック** パネルは、ページをまたいだ複数選択、用途と説明の入力、並べ替え、バインド解除に対応します。トラフィックのページでも、複数のレコードを一度に選び、既存の脆弱性 1 件へ紐づけられます。タスクが継承した脆弱性の証拠は読み取り専用です。変えるには、元のタスクへ入ってください。

システム設定の **Agent 自動トラフィックバインディング** は、既定ではオフです。読み書きのインターフェースは `/api/settings` の `agent_traffic_binding` です。オンにすると、リクエスト／レスポンスの閲覧、ツール呼び出し、プロンプトに由来する Token の消費が増えます。新しい設定は、次のラウンドの Agent から有効になります。オフのあいだは、自動バインドのパラメータと補完バインドのツールは隠れ、自動バインドの案内は注入されず、すでに動いているセッションが新たに提出する自動バインドは拒否されます。手動のバインド、トラフィックのキャプチャ、保存済み証拠の読み取りとエクスポートは、影響を受けません。

機能をオンにしたあとの既定の流れは、検出結果の保存 → レポート Agent の自動起動 → トラフィックの照合とバインド → 最新の証拠バージョンに基づくレポートの作成、です。報告者は `evidence` に、検証コマンド、主要な出力、すでに手元にある実際のトラフィック ID とその用途を残します。レポート Agent は、脆弱性の詳細と実行記録を合わせ、`traffic_search` / `traffic_get` で確認してから `bind_finding_traffic` を呼び出し、最新の `version` を読んでレポートを保存します。スイッチがオフのとき、レポート Agent は生トラフィックの検索／読み取りツールを追加では受け取らず、自動バインドもしません。手動でバインドしたスナップショットは引き続き読め、レポートも生成できます。

既存の呼び出し元とも互換です。`report_finding` の `traffic_refs` / `evidence_hint_id` を使えば、これまでどおり明示的に、その場でバインドできます。バインドは任意です。TCP のような非 HTTP の脆弱性であるとき、まだ何も収集していないとき、正確なレコードが見つからないときは、参照を省いても、通常どおり報告し、レポートを書けます。コマンド出力やログなど、ほかに検証できる証拠を残し、バインドしなかった理由を説明することを勧めます。必須の入力フィールドは新しく増えません。提出する ID はすべて有効で、本文が無傷でなければなりません。1 件でも失敗すると、この呼び出しのバインド操作全体がロールバックされます。報告と同時の明示的なバインドが失敗すると、報告全体がロールバックされます。同じスナップショットを重ねて追加しても、バインドは増えず、説明も上書きされません。

## Agent の ID 体系とレポートのバージョン

`report_finding` に新しい任意パラメータを追加しました。配列の順序が、最初の証拠の順序です。

```json
{
  "traffic_refs": [
    {"traffic_id": "real traffic ID", "role": "baseline", "note": "normal account request"},
    {"traffic_id": "another real traffic ID", "role": "proof", "note": "reproduction request"}
  ]
}
```

用途は `baseline`（正常時の対照）、`proof`（脆弱性の証明）、`verification`（補足の検証）、`supporting`（補助証拠。既定）です。まず `traffic_search` / `traffic_get` で、実際のレコードと照合してください。ドメインとタイムスタンプは、候補を絞るためだけに使い、タスクへの帰属を決めつけないでください。

プロンプトは [CyberStrikeAI の脆弱性報告ツールの案内](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go) を参照し、このプロジェクトの任意バインドの規約と組み合わせています。バインドしなかった理由を必須にする規則は加えていません。ID を推測してはならず、証拠を埋めるためだけに繰り返し探るべきでもありません。

戻り値の 1 行目は、これまでどおり `finding recorded: <探索ノード ID>` です。続く JSON は、独立した脆弱性レコードの `finding_id`、探索ノードの `finding_node_id`、バインドの要約を渡します。

- `get_finding_traffic(finding_id)` は **独立した脆弱性レコードの ID** を使い、順序付きの一覧と `version` を返します。`binding_id`、`side=request|response`、`offset`、`length` を渡すと分割して読め、1 区切りの上限は 8192 バイトです。
- `update_finding_report` の `finding_id` は、**引き続き探索ノードの ID を使います。** 新しく追加した `evidence_version` には、実際に読んだバージョンを入れてください。レポートを生成しているあいだに証拠が変わると、古いバージョンからの書き込みは拒否されるので、読み直して生成し直す必要があります。
- 古いレポートの呼び出しがバージョンを渡さない場合、既存のトラフィック証拠を上書きしたとは扱いません。バインド、説明、用途、並べ替えが変わると、既存のレポートには更新が必要である印が付きます。

自動バインドがオンのとき、`add_hint` / `add_task_hint` は、単一のヒント、または一括の `hints` の各要素に `traffic_refs` を保存できます。プランナーが誰かに代わって報告するときは、`evidence_hint_id` を渡して、このタスクに対応するヒントの中の参照を、曖昧さなく選べます。継承されたヒントは参照できません。システムは、ドメイン、タイムスタンプ、閲覧履歴からバインドを推測しません。提出が失敗しても、中途半端な脆弱性は作られず、レポートが早まることもありません。

既存の脆弱性にバインドが欠けているときは、再登録せずに `bind_finding_traffic(finding_id, traffic_refs)` で補えます。`list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` は、明示的な `finding_id` と `finding_node_id` を返します。古い `id` は、探索ノードの意味のままです。

起動時には、古いツール schema へ任意プロパティを追加するだけです。もともとの既定のトラフィックツールのバインドはレポート Agent にまで広げ、補完バインドのツールは、既定ではレポート Agent に任せます。カスタムのバインド一覧、プロンプト、説明、有効状態は、そのまま保ちます。案内は、最終的なツールの組み立てが終わったあと、まとめて追加します。報告ロールは、すでに手元にある証拠を引き渡す責任を持ち、レポート Agent は、照合、バインド、レポート作成の責任を持ちます。プラットフォームの会話にタスクの文脈がないときは、構造化されたヒントとしてタスク Agent に引き渡さなければならず、直接報告してはなりません。タスクの完了を判断する前に、まず手元の証拠を引き渡します。バインドするトラフィックがなければ、待つことは強制しません。失敗した `report_finding` は、レポート Agent を起動しません。

## API

基底パスは `/api/exploration/findings/{finding_id}/traffic` で、独立した脆弱性 ID を使います。認証は既存の方式に従い、`context_task` が、タスクの可視性と、継承された読み取りが読み取り専用かどうかを検証します。

各メソッドと相対パスのリクエストと戻り値は、次のとおりです。

- `GET`: 順序付きの要約、証拠のバージョン、レポートが採用したバージョンを返します。
- `POST`: `{"traffic_refs":[...]}` を 1 回のバッチで追加します。
- `PATCH /{binding_id}`: `{"version":1,"role":"proof","note":"description"}` で編集します。
- `DELETE /{binding_id}`: `{"version":1}` で削除します。
- `PUT /order`: `{"version":1,"binding_ids":["2","1"]}` で並べ替えます。一覧は完全でなければなりません。
- `GET /{binding_id}`: スナップショットのメタデータと、長さを制限した本文のプレビューを返します。
- `GET /{binding_id}/body`: `side`、`offset`、`length` を受け取り、`download=1` のときは完全な生バイトをダウンロードします。

バージョンや並べ替え集合の衝突、あるいはアーカイブ進行中の書き込みは `409` を返します。継承された項目への書き込みは `403`、存在しないかその脆弱性に属さないバインドは `404` を返します。トラフィックや添付の読み取りと検証に失敗したときは、はっきりしたエラーを返します。

## 保存とマイグレーション

起動時に、PostgreSQL に対して冪等なマイグレーションを実行します。`traffic_evidence_snapshots` と `finding_traffic_bindings` のテーブル、および `findings.evidence_version` / `report_evidence_version` の列（既定は `0`）を新たに追加します。過去のテキストから補完バインドを推測することはありません。

スナップショットは、元のトラフィック ID、キャプチャ時刻、URL、メソッド、ステータス、リクエスト／レスポンスのヘッダ、本文の長さ、SHA-256 を保存します。本文はハッシュに基づき `<data>/evidence/blobs/<先頭2文字>/<hash>.bin` に置き、クリーンアップ対象の `data/traffic` とは分けてあります。複数の脆弱性が、スナップショットと本文を共有できます。スナップショットには内容を更新するインターフェースはなく、検証が一致しなければ、読み取りとエクスポートは失敗します。

元のトラフィックの書き込みロックのもとで、大きな本文 blob と古いディレクトリのレコードを含め、本文全体を読みます。まずファイルを永続化して検証し、そのあと 1 つの PostgreSQL トランザクションで、探索ノード、インテントの関係、脆弱性、スナップショット、バインドを記録します。コミットのあとではじめて、プランナーに通知します。失敗したとき、参照されないファイルが残ることはありますが、途中までしか記録されていない業務レコードは作りません。

PostgreSQL のアドバイザリロック `7337741004` が、証拠ファイルと SQL の参照を調停します。タスクの行ロックは、アーカイブのキューに入ったあとの証拠の変更を禁じます。リストアは、本文のインストールからメタデータのコミットまで、処理全体で証拠ロックを保持します。脆弱性を削除すると、バインドも連鎖して削除されます。

クリーナーは 1 時間ごとに動き、参照されておらず、進行中でもないタスクの内容だけを回収します。最短でも 24 時間は待ちます。通常のトラフィックのクリーンアップは、証拠ディレクトリに触れません。ホットデータをバックアップするときは、PostgreSQL と `data/evidence` を一緒にバックアップしてください。

## エクスポートとアーカイブ

Markdown には順序付きの証拠一覧とバージョンが入り、JSON にはメタデータが、CSV には件数とバインド ID が加わります。`md-zip` は脆弱性の Markdown を保ったまま、次の構造も一緒に提供します。

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown は相対リンクでパケットを参照します。ダウンロードを送る前に、添付のコピー、ハッシュの検証、圧縮、ディスクへの同期、そしてすべての ZIP エントリの CRC 読み取り検証を終えます。エントリが欠けているか壊れていれば、ダウンロード全体が失敗します。完全な添付は、生のバイナリのバイトをそのまま保ちます。

アーカイブ v3 は、脆弱性のバインド関係に従ってスナップショットと本文を集め、元のトラフィックやドメインには依存しません。パッケージの検証が終わってからホットデータを消し、共有されている証拠は残します。リストアは、まずインストールした本文を検証し、そのあとトランザクションでメタデータとバインドを復元します。失敗したときは再試行できます。v1 / v2 も引き続きリストアでき、欠けている新しいフィールドは明示的に `0` で埋めます。

## 検証と境界

各テストパッケージは、`ARTEX_PG_DSN` で指定する、自分専用の新規 PostgreSQL テストデータベースを持ちます。残ったタスクやモデルのフィクスチャが、バックグラウンド実行を引き起こさないようにするためです。関係するパッケージのテスト一式を実行し、設定不足のためにスキップされたテストがないことを確認してください。

```sh
# 各パッケージを実行する前に、ARTEX_PG_DSN を該当する隔離されたテストデータベースへ設定します。明示的な設定に失敗した場合は、必ずエラーにしなければなりません。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証には、`npx tsc --noEmit`、影響を受けたファイルの Biome 検査、Webpack ビルド、`NEXT_EXPORT=1` の静的エクスポートが含まれます。実行中の開発サーバーを上書きしないよう、別のキャッシュディレクトリを使ってください。

ローカルのエンドツーエンドの受け入れ検証は、別ポート、制御された HTTP / ドメイン HTTPS の標的、一時データディレクトリを使います。2 つのバインドの入口、ページをまたいだ選択、並べ替えと説明、エラーの案内、継承された読み取り専用、ダウンロードをカバーします。元のトラフィックを削除したあとのエクスポート、アーカイブ、ホットな本文の回収、ハッシュ検証を伴うリストアも含みます。

最初の版は、グローバルな証拠の調停ロックを使います。大量のバインドやエクスポート、あるいは遅い添付のダウンロードが進んでいるあいだ、ほかの証拠操作は待つことがあります。記録も完全な本文もなければ、証拠を作り出すことはできません。この機能はキャプチャのスイッチを変えず、HTTPS で IP に直接アクセスするときの証明書の問題も扱いません。
